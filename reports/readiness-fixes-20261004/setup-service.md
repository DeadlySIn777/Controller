# IS-2 disconnected setup service implementation

Implemented in `controller_config/setup_service.py`, with focused tests in `tests/test_setup_service.py` and public adapter acceptance in `tests/test_setup_cli.py`. This is a new versioned, file-only setup service. Existing six/two model, configuration, recovery and runtime files were not changed by this workstream. No routing, CAD, electrical source, target firmware, external interface archive or existing machine settings were changed.

## What works

- A complete requirements/resource manifest represents twelve motor channels with separate enable and alarm, four ABZ ports, 24 general inputs and sixteen outputs. Motor resource IDs are `SIM.M0` through `SIM.M11`, with explicit user labels M1 through M12. Resources are explicitly unobserved and not physically qualified. Other required analog/process/comms/protection/accessory functions remain visible as required but unconfigurable in this bounded fixture. Integrated regions are not represented as removable cards.
- Four simulation profiles cover a three-axis mill, a four-motor dual-X gantry, an eight-motor machine and a twelve-motor machine. The full twelve-channel manifest remains available regardless of configured motor count. There is no licensing or display-based channel removal.
- Typed draft templates leave six mechanical/rate facts per drive missing. `example_draft()` supplies an explicit opt-in demonstration recipe: 200 full steps/revolution, 16 microsteps, 1:1 transmission, 5 mm/load revolution and 10 mm/s. These are simulation examples, not identified equipment or qualified physical settings.
- One validator calculates pulses/revolution, mechanical ratio, steps/unit, normalized steps/mm, required pulse rate and timing margin using decimal arithmetic. It checks per-drive timing/polarity, exact simulation equipment identity, topology/resource conflicts, explicit units, input voltage, encoder counts and the retained 0.5 A/channel and 2 A/four-output-group limits. The 100 kHz simulation ceiling is an authored fixture limit, not a CNC3/FPGA/drive rating.
- Missing facts and unsupported selections are structured and saved for resume. Unknown fields and invented commissioning/homing/permission claims are rejected. Terminal instructions only contain `SIM.*` labels.
- Switching profiles archives the outgoing draft under its profile ID in the same atomic store, including through a direct cross-profile commit. `status().retained_profile_drafts` exposes up to four supported drafts for resuming a larger profile without losing its extra motor answers. These are unverified selections, not additional committed configurations. Early schema-1 stores without the additive field remain readable without rewriting bytes; their next mutation adds the map. Retained drafts are validated for schema, profile identity and absence of invented authority.
- Preview is read-only and binds store identity, local simulation epoch, revision, complete state digest, catalog digest, candidate, deterministic diff and recalculated validation. Commit independently recomputes those fields and uses the existing same-filesystem atomic-write infrastructure with a new setup-only OS advisory lock. Duplicate request IDs return their persisted result without applying twice. An ID reused for a different retained plan fails.
- The stable `<store>.setup.lock` file uses a nonblocking Windows byte-range lock or POSIX `flock`; it is never unlinked. OS ownership ends on process death, so a crashed setup writer does not permanently block resume. A prior `<store>.lock` sentinel fails closed with `STORE_BUSY` and is not automatically removed, preserving the boundary with older setup builds. The legacy configuration service and budget locking implementations are unchanged by this workstream.
- Initialize, draft save and epoch restart return a detached snapshot of the exact state held under their write lock. An intervening writer cannot substitute a newer revision into an older caller's reply and thereby authorize overwriting that writer on the next autosave.
- Previous active configuration generations can be previewed and restored as a new generation. Restoring the current active configuration can discard a pending draft without fabricating a new active generation. Audit entries retain actor, revision, generation, request, before/after configuration digests and restore source. The last twenty prior generations, one hundred request results and two hundred audit events are retained. An older plan outside request history still fails its stale revision/state binding; unknown request outcomes must be inspected rather than blindly retried.
- The same service and JSON schema are available to the main implementation's CLI and local frontend. No physical transport or actuation method exists. Every status/preview/result carries simulation-only, permanently unverified physical commissioning, inhibited outputs, unhomed state, no motion authorization and an empty machine-command list.

## Public interface

`SetupService(store_path)` does not create files. `initialize(actor='local')` explicitly creates its own checksummed store and refuses existing foreign/corrupt stores. `status()` returns an uninitialized result gracefully when the path does not exist.

Catalog/schema calls: `capabilities()`, `profiles()`, `equipment_profiles()`, `schema()`, `draft_template(profile_id)`, `example_draft(profile_id)`.

Intake/transactions: `validate_draft(draft, require_complete=False)`, `missing_facts(draft)`, `save_draft(draft, expected_revision, actor='local')`, `preview(draft=None)`, `commit(plan, request_id, actor='local')`, `restore_preview(generation)`, `request_result(request_id)`, `audit()`. `restart_epoch(expected_revision, actor='local')` invalidates outstanding local previews; it is not a hardware reset.

Errors use the existing `ConfigurationError` structured code/message/path contract. Validation returns missing facts separately from semantic blockers; complete validation rejects either. Saving a structurally valid incomplete or unsupported draft is allowed, but preview/commit requires a complete valid simulation configuration.

## Validation performed

`python -B -m unittest discover -s tests -p test_setup_service.py -v`: **29 tests passed**. Tests use only temporary stores and authored simulation data. Cases cover all four profiles and full channel counts; preserved historical six-motor capabilities; ratio/inch/mm calculations; exact rate boundaries; timing, current, group and voltage refusals; missing encoder facts; unsupported equipment; duplicate/unknown resources; nonfinite/bool/huge/wrong-unit input; invented physical authority; interrupted atomic replacement preserving old bytes and cleaning temporary files; concurrent clients; stale epoch/foreign store; changed/resealed plans; independent derived-value checks; idempotent replay after reopen; generation restore; pending-draft discard; corruption/catalog-change refusal; numerical JSON representation preservation; retained twelve-motor answers after changing to three motors and reopening; direct cross-profile commit; retained-draft corruption refusal; and read-only compatibility with the initial schema-1 layout.

Three deterministic interleaving regressions inject a second client immediately after the first client's lock releases. They cover changed/no-op draft saves, fresh/existing initialization and epoch restart. All reproduced the old post-unlock status-read defect before repair (five subcase failures), then passed with locked snapshots. The original caller keeps its own state/revision and its subsequent stale write is rejected while the second client's draft remains intact.

A real subprocess acquires the OS lock; a competing live writer receives `STORE_BUSY` without changing the store. The test forcibly kills the owner without running its cleanup, reopens the service and successfully saves the retained draft while the same lock file remains. A separate regression leaves a legacy sentinel intact and verifies fail-closed behavior. This process-death test ran on Windows; the POSIX branch is source implementation, not a POSIX execution result. Cross-computer/cloud-synchronized locking and physical power-loss durability are not established.

`python -B -m unittest discover -s tests -p test_setup_cli.py -v`: **12 tests passed**. These run the actual CLI in subprocesses against temporary directories: discovery without file creation, explicit examples, incomplete-draft resume, eight-motor preview/commit/idempotent retry/restore, epoch invalidation and request-result recovery, Unicode machine names, export overwrite protection, retention of twelve-motor answers across a smaller profile, optional AI capability discovery, structured rejection of invented authority, and offline guidance reporting actual rate/unsupported-equipment blockers without changing saved facts. Negated, informational and injected motion/job requests produce no commands, no paid calls and no state mutation. The initial run exposed Windows stdout codepage corruption; the parent workstream changed JSON output to ASCII escapes, and the Unicode/blocker regressions now pass without forcing a UTF-8 environment.

An initial incorrect unittest module invocation was corrected to discovery because `tests` is not an importable package. A first test run exposed a `ConfigurationError` being caught as its `ValueError` parent during plan digest checking; the handler was corrected and the full focused suite rerun successfully. These are host/source tests only.

## Remaining boundary

There is no actual hardware discovery, approved real equipment catalog, protected physical settings-media driver, whole-board service proof, calibration/commissioning execution, target CNC3/HAL activation, model API client or manufacturing qualification in this file. Saved selections and source hashes are not trusted physical measurements. The checksum is corruption detection, not authenticated authorship. Filesystem replacement tests do not establish physical power-loss durability. The main workstream separately owns frontend/CLI and the budget workstream owns paid-call reservation logic.

This closes the absence of a usable IS-2 **disconnected** setup representation and shared deterministic transaction core. It does not close physical setup, customer-ready firmware, AI expert evaluation or manufacturing gates.
