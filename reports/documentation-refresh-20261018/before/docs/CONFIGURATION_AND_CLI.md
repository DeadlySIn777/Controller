## Proposed CLI surface

`cncctl` is the proposed product command name, not an installed executable. Run the file-only prototype with `python -m controller_config`; its exact supported commands and API example are in the [configuration walkthrough](../examples/configuration/README.md). Table entries below include future operations that this prototype does not implement.

| Command family | Customer/assistant purpose |
|---|---|
| `capabilities`, `schema` | Discover installed board revision, firmware, I/O types, supported operations and limits. The prototype always emits JSON; its optional `--json` flag is a global option and must precede the subcommand (`python -m controller_config --json capabilities`), not follow it |
| `profile list/import/export` | Reuse versioned machine, drive, spindle and accessory profiles |
| `module inspect`, `plasma compatibility` | Match module, harness, source and calibration records; report changed setup dependencies |
| `device discover --read-only`, `device inspect/test-read` | Discover supported transports and validate selected third-party profiles without issuing output commands |
| `config show/validate/diff` | Read and preview changes without applying them |
| `config apply/rollback` | Apply validated transactions while the required stopped/maintenance state holds |
| `wiring plan/check` | Generate terminal-by-terminal guidance and report which checks require physical measurements |
| `diagnose --json`, `power status --json` | Report stale signals, board faults, eFuse trips, voltage/current readings and helpful next checks |
| `commission` | Guide input polarity, limits, travel, scaling, homing, spindle and registration checks |
| `job validate/preview` | Check a named job against the active machine/setup revision and available implemented checks |
| `firmware inspect/stage/activate/rollback` | Reproducible, compatible update/recovery flow with outputs inhibited |
| `cartridge inspect/export`, `replacement preview/apply` | Future product spelling; the prototype implements these today as `cartridge inspect/save` and `recovery bootstrap-preview/replace-preview/apply` (see below). Proposed shared-service operations: validate machine-memory records, compare installed modules, preserve assignments and require affected verification; no direct output authority |

Every supported UI operation needs an equivalent documented API/CLI action where practical. Structured output includes schema version, stable error code, units, source timestamp and active configuration revision. Help and schema discovery must work offline. Commands must return bounded output and meaningful exit codes; interactive confirmation must have an explicit automation equivalent with scoped authorization, not a hidden global "unsafe" flag.

## Configuration rules

- Store machine settings in a typed, versioned schema: units, channel capabilities, polarity, limits, scaling, timing and firmware dependencies are explicit.
- Plan/validate/diff before applying. Save previous versions and provide atomic updates and rollback after interruption. Unknown keys, unsupported pins, conflicting roles and out-of-range values fail validation.
- Base limits come from the installed hardware identity and commissioned machine profile. AI-generated settings cannot redefine those limits or claim that a probe/homing test happened.
- Assign one owner for machine-affecting commands. Disconnected/restarted agents lose authority; delayed results cannot apply to a different boot or setup revision.
- Record who or what requested a change and the exact before/after configuration. A changed fixture, scale or kinematic parameter invalidates the dependent checks.
- Keep developer extensions isolated from the real-time thread. Resource and electrical budgets are part of module compatibility, not just connector shape.
- Distinguish observed module/adapter identity, selected downstream model and independently verified wiring/calibration. Detection alone cannot establish a cutter's divider setting or identify the VFD behind an RS-485 adapter.
- Bind device replacements to new connection/configuration epochs; discard stale queued commands. Preserve unaffected calibration data, invalidate dependent checks and never automatically fire a torch or restart a spindle on reconnection.
- Installed capabilities describe fitted hardware, deployed drivers and qualified profiles. Never generate them from the [200-feature planning catalogue](FEATURE_CATALOG.md).
- Compatibility records must distinguish exact tested third-party hardware from a generic or customer-authored profile. A kit may supply a preferred peripheral, but a listed ordinary component can be sourced elsewhere and must use the same validation and commissioning path.
- Licence and capability checks must work offline. A supported replacement module is a service event, not a reason to repurchase an existing software entitlement; a new expansion capability may have a separate entitlement when the offer states that clearly.

The [plasma contract](PLASMA_MODULE_SYSTEM.md) and [third-party Modbus contract](THIRD_PARTY_MODBUS.md) define the proposed specialized records and acceptance cases. Their commands remain future API design; no new hardware discovery or Modbus control implementation is claimed.

The [replacement demo](../reports/MODULE_REPLACEMENT_DEMO.md) exercises a file-only `RecoveryService` using the existing configuration service for actual store writes. The later [public recovery CLI](../reports/RECOVERY_CLI.md) now exposes `cartridge inspect/save` and `recovery inventory/bootstrap-preview/replace-preview/apply` through `python -m controller_config`. It models one virtual home-input bank and explicit new-compute import. A replacement changes no configuration revision but records a same-revision `replace_module` entry in the shared audit. Production cartridge authority, physical discovery and automatic guided recovery remain future integration work.

The [persistent actual-runtime service](../reports/PERSISTENT_RUNTIME.md) is available as `python -m controller_config.persistent_runtime --directory <authority-directory>` inside the isolated LinuxCNC/RTL profile. It provides status, explicit new-machine initialization, preview/apply, reconciliation and interrupted-save recovery. Startup remains inhibited until the machine/profile/capability-bound records are validated and activated; recovery does not restore homing or enable motion. Absolute deadlines are checked at HAL publication and again in the compiled cyclic handler. This implements only XYZ step scales, separate from the full-machine/cartridge schema and field-I/O fixtures. The earlier `controller_config.runtime` apply/recover commands are available only for explicit volatile laboratory operation and cannot bypass the persistent default. Both contracts share the same stopped activation core; Python is outside cyclic motion. Their pulse-rate check keeps a margin derived from the compiled CNC1 write path: the driver requests a whole number of counts per servo period and latches `CNC1_RANGE` above the discovered DDS ceiling, so a scale is accepted only when scale x joint `MAX_VELOCITY` <= ceiling - 2 counts / `[EMCMOT]SERVO_PERIOD` (one count for rounding the target, one for its one-cycle lag correction). For the current profile that is 195312.5 - 2000 = 193312.5 steps/s, or 19331.25 steps/mm at 10 mm/s; the former ceiling-only check accepted up to 19531.25. A missing or unusable servo period (anything other than 1 to 18 ASCII decimal digits, or outside 1 ns to the 10 ms outer ceiling) refuses every scale preview, apply and saved-record load with `CAPABILITIES_UNAVAILABLE`. The service also applies the compiled driver's servo-period rule. `cnc1_write` refuses a period above half the discovered RTL watchdog with `CNC1_CONFIG` before any frame, where `watchdog_ns = watchdog_ticks x 10^9 / core_hz` (integer division, then halved again with integer division). The service reads `cnc1.watchdog-ticks` and the discovered `core_hz`, mirrors the same integer arithmetic, and refuses a longer period with `SERVO_PERIOD_LIMIT`. For the default RTL (250000 ticks at 50 MHz) the bound is 2.5 ms, so the shipped 1 ms profile is accepted; exactly 2.5 ms is accepted and 2.500001 ms is refused. A missing, zero or non-integer watchdog or `core_hz` refuses with `CAPABILITIES_UNAVAILABLE`. The pulse-rate margin is derived only for a period that passes this check. The period and watchdog are carried as separate top-level `servo_period_ns` and `watchdog_ticks` snapshot fields and bound into each volatile plan, so a changed value makes an earlier preview `RUNTIME_STALE`. They are deliberately not added to the `capabilities` dict stored in `cnc1-persistent-scales/1` records, which must match exactly on reload. A non-zero `cnc1.config-result` is reported as `COMPILED_GUARD_REJECTED` with a name for the code (for example `persistent-authority gate`); the message still ends with `code N`. Authorities saved before the margin was introduced therefore keep the same identity and still activate (host test against the archived pre-margin generation-2 authority); their scales are re-checked against the new limit on every load, and the period itself is bound to saved records through `profile_sha256`, which hashes the `controller.ini` that holds `[EMCMOT]SERVO_PERIOD`. A saved scale above the new limit is refused with `PULSE_RATE_LIMIT` and the inhibit stays held. This is a consistency check against the driver's arithmetic, verified by host tests; it is not a drive or jitter qualification.

## Simple first-use flow

The [repair/memory contract](MODULAR_REPAIR_AND_MEMORY.md) adds recovery into replacement electronics. Store complete machine settings independently of firmware and module factory calibration. Keep current same-store `backup/restore` behavior intact; a replacement compute unit needs a separate explicit machine-identity binding and preview/apply transaction. Any replacement plan binds the observed module set, cartridge generation/digest, store revision and runtime epoch, and rechecks them before committing. Restoring configuration never restores live homing, job/run permission or claimed physical commissioning. Firmware/package compatibility and affected verification use the same service across CLI and UI.

Choose a supported machine/drive profile; attach named modules; show a diagram with the actual terminal names and expected wire functions; run guided input and power checks; verify direction and scaling under the machine's commissioning procedure; establish limits/homing and measured registration; then save a reusable profile.

Software cannot infer arbitrary wiring from connector occupancy. Distinguish detected evidence from user-confirmed wiring and measurements. Use keyed/labeled connectors, accessible test points and indicator/fault reporting where their value justifies the cost. Advanced setup should remain available, while the ordinary supported-machine route avoids hand editing and CAD expertise.

## Acceptance evidence before claiming this experience

1. A fresh system can be configured using only documented CLI/API calls, with the same result as the UI.
2. An assistant can discover the schema, propose a change and receive a meaningful diff/error without private implementation knowledge.
3. Interrupted updates roll back or recover into a known disarmed configuration.
4. An inexperienced user wires and commissions a representative supported setup using the generated guidance; record actual mistakes and interventions.
5. Invalid voltage/channel assignments, stale proposals and conflicting configurations are rejected by the backend independently of the UI or assistant.
