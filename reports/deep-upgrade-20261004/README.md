# Deep software, firmware and UI upgrade — 4 October 2026

The user requested a substantially deeper audit and actual upgrade, with an exceptionally easy dark/red frontend, reliable assisted setup and the approximately $15 API allowance protected. Three independent workstreams audited setup intelligence/accounting, recorder/state/archive integrity, and diagnostic firmware/runtime/recovery. Reciprocal reviews found additional defects and verified their corrections. Claude's routing remained untouched.

## Applied experience upgrade

- **Local fact intake:** explicit supported motor statements produce a candidate with original source quotes, conflicts and unresolved text. Saved answers are retained. Twelve motors and 72 mechanical facts were interpreted in the actual browser with zero provider calls, then explicitly added, validated, reviewed and committed. Supported syntax is bounded; this is not automatic arbitrary-manual interpretation or a qualified physical CNC setup specialist.
- **Readiness:** a new common `ReadinessService`, public CLI and sixth UI view report the exact configuration binding, settings integrity, missing mechanics, timing/electrical blockers, reviewed generation and diagnostic availability. The next step comes from these checks. Physical commissioning stays unavailable, and no health percentage or machine permission is invented.
- **Configuration self-check:** actual saved settings are independently recomputed; shortened direction timing is rejected for each configured motor; 0.6 A output selection is rejected against the retained 0.5 A limit; an actual checksummed tar/Zstd backup is written privately and roundtripped byte for byte. A twelve-motor receipt contains 15 checks and binds store, epoch, revision, generation, active configuration and draft digests. This checks configuration/storage only: `motion_loop_tested=false`, `physical_measurements=0`.
- **Reviewed browser recovery:** choose a local compressed backup, select its reviewed generation or working draft, inspect calculated settings and a readable before/after diff, then save through the original canonical commit payload. Uploads are limited to 8 MiB and archives are never extracted or executed. Imported settings cannot restore homing, position or output permission.
- **Native downloads:** real JSON, configuration and support downloads now work in the in-app browser. The failed Blob-download path was replaced with native URL downloads. A separate random HttpOnly/SameSite=Strict read-only credential accepts only the four named GET export routes; it cannot authorize writes or act as the setup header token. The cookie name is port-specific; cookies themselves are not port-isolated. Existing header-token precedence, exact Host and mutation Origin checks remain.
- **Bound saves and refreshed drafts:** status returns a draft binding. UI saves carry store ID, epoch, revision and original draft digest; service and optional CLI binding checks occur under the writer lock. Refresh adopts a newer saved draft only when local edits are already saved, preventing a new revision from authorizing an old cached draft. Actual browser verification preserved another local client's saved name and then completed a normal bound save.
- **Dark/red interface:** the semantic palette, labelled status colors, keyboard focus and touch controls remain. Readiness uses a compact checklist with expandable source evidence; review shows changed fields before the complete source diff.

Follow-up questions are generated from the candidate's actual missing fields; provider questions are retained only for source inspection. Paid extraction still has one bounded generation request, zero automatic retries, explicit opt-in and retained uncertain charges. No paid request was made.

The [recorder/state/archive audit](storage-audit.md) fixes first-commit orphan recovery, interrupted manifest publication, source acknowledgment inconsistencies, bounded/safe file reads, held/hard-linked lock handling, erroneous pre/post gap overlap, producer sequence/timestamp regressions, older-fact fallback after conflicts, contradictory fresh producers at different timestamps, incorrect boolean response units and ambiguous archive publication acknowledgments. Raw records remain preserved and malformed/conflicting evidence cannot establish a healthy state.

The [firmware/runtime audit](firmware-runtime-audit.md) fixes late polls refreshing an already expired diagnostic watchdog; DIC observations before a sample; saturated observation ages becoming fresh again after the 32-bit timer wraps; NaN/negative/boolean velocity acceptance; malformed historical capability/stopped-state guards; missing homing observations releasing modeled inhibit; huge DDS ceilings escaping structured validation; and interrupted virtual cartridge writes truncating unrelated hard-linked files. Diagnostic target outputs remain LOW. Frozen protocols, timing limits, twelve fitted motor interfaces and retained electrical limits are unchanged.

The [reciprocal review](reciprocal-storage-runtime-review.md) includes four real temporary-store substitutions rejected by readiness's full binding and independent firmware/runtime rechecks. The old six-joint/two-encoder and XYZ fixtures remain historical, separate from twelve-motor configuration and the new diagnostic firmware builds.

## Remaining product gates

Physical equipment identities/manuals, actual LinuxCNC/twelve-channel runtime integration, live trusted acquisition, calibrated commissioning, measured timing/current/thermal/safety behavior, current-source HDL/C integration replay, FPGA vendor fit/timing, qualified signed staged updates and whole-motherboard replacement remain open. Paid-model accuracy, billed cost per successful supported setup and novice-user completion still require evaluation. The recorder's host durability checks do not qualify flash wear or physical power-fail behavior. Firmware compilation does not prove target execution. No manufacture/release gate was promoted.

The new configuration self-check is one bounded part of [flagship acceptance](../../docs/FLAGSHIP_WORKFLOW.md). Verified job geometry/collision protection, automatic tuning, universal device discovery and physical self-test are not implemented by these changes. Historical receipts remain tied to their original source; r01, r02 and r03 are separate records, never overwritten or restamped as if one run covered all revisions.
