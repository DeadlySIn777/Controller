# Setup intelligence and allowance audit — 4 October 2026

The earlier adapter proved that a proposed number occurred somewhere in a quoted substring. It did not prove that the number described the requested motor, mechanical field, selected unit or positive statement. A fake provider could consequently propose a motor's full-step count from another motor's data, a microstep value, a negated sentence or contradictory source statements. Ordinary numeric validation cannot detect those semantic errors.

`controller_config/setup_facts.py` now associates each supported statement with an exact configured logical motor ID and mechanical field. It accepts complete positive statements, requires explicit configured units on travel/velocity, distinguishes field phrases from nested words, retains repeated identical facts and blocks conflicting, conditional, negated and incompatible-unit statements. A bare number cannot ground a field. Supported syntax is deliberately bounded; unrecognized text remains visible and unresolved. This is not an arbitrary-manual parser, equipment approval or physical verification.

`local_intake(service, facts, *, expected_revision)` in `setup_assistant.py` creates an offline review candidate. It retains the original source text and quotes, preserves already saved values, lists conflicts and unsupported text, calls the actual shared validator and rechecks store ID, epoch, revision and draft digest before returning. A full authored three-axis intake of 18 facts validates with zero paid/provider calls and no saved-draft change. Independent accepted facts survive an unrelated conflict. Only the ordinary service preview/review/commit can save a candidate. Twelve configured motors and 72 missing facts are grouped into six mechanical questions, with known answers omitted.

The optional paid adapter uses the same evidence association. Its context now binds the capability/profile/equipment catalogue digest and its extraction-policy version is 3, including the complete client acceptance binding. Older caches remain on disk but are not treated as version-3 results. Every result carries store ID, epoch, revision, profile ID, saved-draft digest and catalogue digest. Reopening a valid version-3 cache checks that binding, immutable no-actuation guards, request/revision identity, model output, source evidence, candidate and current deterministic validation before returning it with zero calls. A valid checksum alone cannot make an incoherent or actuating result usable. Existing configuration blockers return a local result without spending.

Authoritative follow-up questions are generated from the candidate's actual validator-reported missing fields. Saved answers and fields filled by the proposal are omitted; the bounded six mechanical groups cannot invent commissioning questions. Raw provider questions remain untrusted source data for inspection and are not the operational guidance list.

Two accounting fixes close concrete failure paths. Budget lock-byte initialization occurs only after OS lock ownership; a concurrently held empty lock is neither mutated nor misreported as an I/O failure. If over-bound provider usage requires a durable freeze and persistence fails, the adapter reports that accounting failure instead of hiding it as an ordinary missing estimate. The durable reservation stays held and repeating the request cannot dispatch another paid operation.

The existing $15 maximum, integer microdollar arithmetic, explicit opt-in, expiring approved prices, one durable reservation, zero automatic retries, no model tools, retained uncertain charges and deliberate final billing reconciliation remain intact. No paid provider call was made during this work.

The focused [verification receipt](ai-verification.json) and [complete test log](ai-verification.log) exercise the actual disconnected setup service, fake transports and native process locks. They cover full and partial intake, wrong logical motor/field, one-based display-label ambiguity, missing/wrong distance and speed units, saved-value conflicts, conditional and negated statements, fractional and extreme numbers, malformed/refused output, prompt-instruction data, stale edits/epochs, policy/catalogue cache invalidation, coherently resealed corruption, missing credentials, timeout liability, failed durable freezes, process death, lost write acknowledgement and concurrent allowance requests. This is host/service evidence. Paid-model accuracy/cost evaluation, trusted billing-provider integration, approved physical equipment records, live controller observations and physical commissioning remain open.

The existing Responses request structure was checked against official [input-token counting](https://developers.openai.com/api/reference/typescript/resources/responses/subresources/input_tokens) and [Responses migration documentation](https://developers.openai.com/api/docs/guides/migrate-to-responses). The adapter continues to use `text.format` for structured output and `store: false` for generation. No default model, provider price or assumed final invoice was added.
