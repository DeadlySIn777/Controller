# Report-local event-storage experiment

This is a separate resource experiment, not the frozen current runtime or an adopted production change. Only event storage is changed. Frozen CNC3 fields, capacity256, original capture timestamp/value/order, all six one-shot capture producers and the fault producer remain present. Up to eight records stage in registers and drain one per clock into a single256x160 synchronous RAM. Occupancy includes both staged and stored accepted records. Only stored, prefetched data can become the acknowledged head. Clear resets validity/pointers without clearing physical RAM. A same-address write/read forwards the new data.

The original banked runtime has64 RAM5K cells. The first serialized map uses8 but raises LUT4 from34,493 to36,225, so this has not closed logic resources. That first experiment also had a staging-pressure bookkeeping defect found by independent review: it counted records even when the staging queue rejected them. The next candidate commits count/pointer/sequence only on successful staging; deliberate impossible-wire-cadence stimulus now latches overflow while preserving the exact accepted count. `serialized-candidate-r02/pressure-r01/historical-execute.log` preserves the earlier failure at cycle7.

The staging bound relies on the **integrated transport**, not arbitrary callers of this private module. Captures arm only through a complete96-byte UPDATE. Even the loose lower bound of one sampled bit per core clock requires768 core clocks between complete commands. Each accepted arm can cause at most six one-shot capture records; the fault producer contributes at most one record per clock. A backlog that is not draining must be accompanied by fault arrivals, which exhaust the256 total-record capacity well before the next legal arm. At most one complete read acknowledgment can coincide within that short interval. Once full, rejected arrivals cannot replenish staging and it drains. This reasoning requires independent review; it is not a formal proof or permission to accept an arbitrary fast arm producer.

The differential fixture compares the whole20-byte head record and status against the frozen banked implementation across160,000 deterministic cycles, including simultaneous captures, timestamp/value changes, fault bursts, overflow, delivery/acknowledgment and clear. It omits head comparisons during the explicitly bounded prefetch window after arm/clear while retaining exact status checks. The actual SPI suite independently checks delivered records and complete command timing. The pressure test deliberately violates the legal transport cadence to verify explicit overflow and exact accepted-record accounting, not to claim those inputs are legal.

Do not adopt solely because simulation passes or RAM use improves. Final map resources, the staging-bound review, mutation controls and the full combined host/provider integration remain necessary. The active `gateware/v3/runtime` files are unchanged by this experiment.
