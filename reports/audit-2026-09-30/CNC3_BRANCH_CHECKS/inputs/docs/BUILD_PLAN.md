# Build plan: cost and hardware first

28 September 2026 UTC. The user wants a Mesa-like selling price **including a touchscreen**, with product options in the **7-, 10-, 12-, 14-, 18- and 21-inch classes and beyond**. The earlier $190 / 21.5-inch FHD reference is one large-screen scenario, not a fixed requirement for every controller. The [display-tier plan](DISPLAY_TIERS.md) defines shared UI, integration and per-package costing. Currency, exact Mesa comparison and selling prices by tier remain unspecified. All dollar comparisons below are explicitly **USD**; they do not assume the user meant USD. Each offered package includes its stated screen in its cost envelope.

## Working production direction

**Immediate integration priority:** [connect the existing six/two implementation end to end](INTEGRATION_MILESTONE.md), using actual LinuxCNC, compiled cyclic CNC1 logic and a replaceable transport backend. Prove feedback and failure handling in RTL simulation before the physical link test. In parallel, complete exact compute/carrier/display cost comparisons and the first disconnected common configuration-service/CLI demonstration. These workstreams do not wait for all 200 features or a finished dashboard.

**Persistent product requirements:** [project memory](../PROJECT_MEMORY.md) and [CLI/customization plan](CONFIGURATION_AND_CLI.md). The user explicitly wants modifiable hardware/firmware, complete machine-readable CLI coverage for chat-assisted configuration, and simple guided wiring/commissioning. These are product acceptance requirements across the following stages, not a claim that the current engineering scripts already deliver them.

**Latest scope revision:** the [platform roadmap](PLATFORM_ROADMAP.md) preserves the user's 200 feature proposals and sets a staged implementation plan. The [eight-motor/four-encoder target](EXPANDED_HARDWARE_TARGET.md) is now the preferred expanded design candidate; the six-joint/two-encoder electrical and cost studies below remain a separately identified baseline. Expanded pin counts, enable topology, rates, power and costs need fresh work. No existing worksheet or test result silently covers the expansion.

**Compute carrier study:** prefer the [CM4/CM5-style dual-connector family](COMPUTE_CARRIER_STRATEGY.md), with exact module compatibility and complete cost qualification. Include [BTT CB2 and CB1](../research/BTT_COMPUTE_REVIEW.md) in the alternatives; the user's estimated offers are separate from observed current retail. CM4, CM5 and CB2 are not automatically interchangeable, and none is a production selection yet.

**Local Linux compute + our own FPGA motion/I/O circuit + ESP32-S3 helper on a custom carrier.** LinuxCNC remains the proposed CNC engine under PREEMPT_RT. CM5 is a measured-cost feasibility candidate; the new bundled-display constraint reopens the compute selection. Its current public pricing does not support a complete profitable Mesa-priced product. The controller owns machining, and an included screen requires a local interface-rendering computer unless a separately costed display computer is supplied. An external customer browser remains an additional interface.

Start the memory study at **2 GB RAM with eMMC**, then justify any increase with measurements. Include the local kiosk browser, GPU driver, representative 3D scenes and CAD conversion in memory, thermal and loaded real-time latency measurements. Qualify each offered display/host combination at native resolution and intended scaling; screen diagonal alone does not determine graphics load or compute tier. Browser workers still consume local CPU and memory; moving a task into a worker does not establish isolation from motion. Bound supported model complexity and schedule conversion work explicitly. Offline use means no cloud dependency. Essential machine execution remains local even when the browser closes.

Purchased x86/Mesa hardware remains an engineering reference, preferably using equipment already available. It is not assumed to be inside each sale unit. The custom FPGA endpoint is now a central product workstream with gateware, driver, feedback and manufacturing work of its own.

**Internal-link study:** investigate dedicated SPI before internal Ethernet, keeping the customer network on the Linux host. The pinned LinuxCNC source explicitly recognizes CM5, but its SPI board lookup needs proper support for our custom board identity and matching gateware. This is a specific development task, not plug-and-play compatibility with a T20. [SPI source audit and proof gates](../research/SPI_FEASIBILITY.md)

The Linux/FPGA/ESP architecture replaces the earlier H7/grblHAL main-controller proposal. It does not add an H7 to this processor stack. ESP-IDF firmware and FPGA gateware remain separate from LinuxCNC. The latest [ESP accessory-automation requirements](ESP_ACCESSORY_AUTOMATION.md) add qualified support-equipment sequences and direct condition monitoring; the current firmware remains read-only diagnostics. Each output has one owner. If machining relies on ESP-confirmed service readiness, lost ESP/link/sensor freshness must trigger the machine's defined response. The ESP has no seamless motion takeover role; independent protection and reviewed defaults must still work when it freezes.

## Cost gate

Verified Mesa manufacturer board prices are **$149 for 7I96S, $219 for 7I76EU and $249 for 7I95T**; these exclude the Linux computer and touchscreen. See the [price snapshot](../research/MESA_PRICE_SNAPSHOT.json). The user's desired bundle therefore asks for substantially more included hardware at a similar price. No exact one of these retail targets has been selected.

In the historical CM5 comparison, the three-part subtotal plus the user's $190 screen reference is **$305.91**, before all remaining electronics, PCB assembly, power supply, enclosure, test or margin. A supplier-advertised $100 21.5-inch sample would reduce that incomplete subtotal to **$215.91**; a $129 15.6-inch retail touchscreen gives **$244.91**. Neither establishes a viable $249 complete product. These are quantity-one scenarios, not production quotes or costs for the full new display range. [Display sourcing study](../research/DISPLAY_COST_STUDY.md)

For illustration only, $249 net selling revenue with a 40% manufacturing gross-margin target permits **$149.40** of manufacturing cost. A $100 display would leave **$49.40 for the entire rest of the unit**, before separately accounted business costs. The margin is not a user-selected requirement. This replaces the earlier $499 board-only illustration, which no longer represented the requested bundle.

Use `allowed manufacturing cost = net selling revenue × (1 − chosen gross margin)` with clearly defined costs. Retail sales tax is not revenue. Distributor discounts, payment fees, shipping subsidies, warranty/support, development recovery and certification/tooling allocations must be accounted for separately and consistently. Gross margin is not net profit.

Cost each complete screen tier at the actual pilot and production quantities separately: one-off prototypes, 10 units, 100 units and 1,000 units. Keep screen size separate from compute and I/O capacity; hold the exact screen package constant within a compute/I/O comparison. Include panel/touch, interfaces, cables, power, mounting/enclosure and final assembly/test. Obtain prices for actual parts and manufacturer assembly/test quotations before claiming a production cost. Do not extrapolate a volume discount that has not been quoted or assume one retail price for all sizes.

Keep a useful core controller and add specifically rated expansion modules for unusual/high-cost interfaces. The [terminal and cost worksheet](CORE_INTERFACE_COSTING.md) now prices a proposed six-joint scope: six differential STEP/DIR channels, six enables and six alarms, two A/B/index inputs, sixteen additional protected inputs, eight additional protected outputs, one 0–10 V spindle interface and defined expansion. Spindle run/direction occupy two of the eight outputs. This is 54 directly mapped digital signals before analog control, host communication and housekeeping. It is not six-axis external encoder feedback. Counts, ratings and rates must be frozen against machine profiles. A cheap base that needs expensive mandatory modules for normal supported operation is not a successful cost reduction.

## Execution plan and gates

**Manufacturing decision:** send the designed boards to PCBWay for turnkey manufacture. Release fabrication files, exact BOM/alternates, placement data, assembly instructions and an agreed programming/test package together. Use PCBWay's actual quotation for parts, fabrication and assembly; other vendors' setup/stencil tariffs are not the estimate. Final display/enclosure integration and functional-test scope require explicit quotation. The PCBWay submission is a user-performed step after the release package exists. The quote must cover fabrication, parts, assembly and programming/test at the study quantities 1/10/100/1,000; the release manifest's `final_cost` stays `incomplete-quotes` until PCBWay's actual figures are recorded. The [PCBWay submission checklist](../manufacturing/PCBWAY_SUBMISSION_CHECKLIST.md) lists the required files and decisions; the design is not ready for PCBWay manufacture. Nothing is authorized for ordering at this stage.

**Optional expansion:** [AI compute plan](../research/AI_ADDON_PLAN.md). Start with an Ethernet-connected companion using its own compute/memory/power; keep ordinary machining independent of AI availability. An internal accelerator socket is conditional on the selected host, electrical/thermal budget and supported software. AI hardware is excluded from the base price comparison.

**Power protection:** [physical fuse plus electronic branch protection](POWER_PROTECTION.md). Coordinate power-entry backup protection, branch limiting and existing protected outputs with the actual supply and load ratings. Fault telemetry belongs in the common CLI/UI; clearing a trip must not automatically resume machining.

**Reliability target:** use the [industrial qualification plan](INDUSTRIAL_QUALIFICATION.md) for whole-unit power, I/O, EMC, environment, software, factory test and service requirements. Cost protected ESP power, required sensors/output drivers, independent watchdogs and qualification explicitly. The proposed HDPE enclosure needs a designed shielding/bonding, mechanical and thermal arrangement. Define per-machine stop/cooling/workholding behavior; component ratings do not become finished-product or safety claims.

**Modular equipment:** implement the [plasma module/harness/profile contract](PLASMA_MODULE_SYSTEM.md) so a qualified cutter upgrade preserves the controller and unaffected table configuration. First prove discovery, selective invalidation and fault behavior with disconnected virtual devices, then qualify a divided-voltage interface and two named harness/source combinations. Keep specialized source-voltage hardware out of the base controller's general inputs.

**Third-party accessories:** support [ordinary USB/RS-485 adapters and Modbus RTU/TCP devices](THIRD_PARTY_MODBUS.md) through tested profiles and the same UI/CLI service. A supported serial VFD does not require our own proprietary adapter. Keep motion pulses, angle/index capture and fast process feedback on their dedicated timing paths.

## First integrated software demonstration

First connect actual LinuxCNC motion and the existing FPGA RTL through CNC1 and exercise feedback/fault behavior. In parallel, demonstrate disconnected profile selection, conflicts, generated wiring, configuration validation, stopped/disarmed apply and backup/restore. Neither requires waiting for a complete cost quote or CAD dashboard. Once the exact UI source is confirmed, extend the shared service into the visual workflow: select one known machine profile; import a representative plate/vise/stock setup; confirm ambiguous units and placement; establish explicitly simulated registration; save/reopen; preview and execute a small job in actual LinuxCNC simulation; disconnect/reconnect and observe actual simulated state without automatic restart. Hardware procurement and final design still require the cost and feasibility gates.

LinuxCNC exposes local command, status and error interfaces that a service can adapt for our UI. That is an integration task; retaining the same interface does not mean its existing Grbl transport works unchanged. [LinuxCNC Python interface](https://linuxcnc.org/docs/html/config/python-interface.html), [build documentation](https://linuxcnc.org/docs/html/code/building-linuxcnc.html)

The exact user-preferred UI reference still needs confirmation. The current FluidCNC candidate has an automatic connection path, so isolate transport before launching a development copy. Do not change or flash the existing machine as part of this prototype.
